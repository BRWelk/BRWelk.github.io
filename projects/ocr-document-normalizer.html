OCR Document Normalizer

A clean-room document-processing application that converts variable inbound purchase-order PDFs into a fixed, machine-readable format while preserving source evidence, human review, exception handling, and an audit trail before downstream automation is allowed to act.

The problem

Automation is only useful when the incoming data is trustworthy.

Purchase orders, invoices, and similar business documents arrive in inconsistent layouts. Even when OCR can read the page, extracted text still has to be mapped into reliable business fields, validated against known rules, and reviewed when the system cannot resolve a value safely.

The application creates a control point between unstructured documents and downstream systems. Instead of sending raw OCR results directly into an ERP, vendor workflow, or accounting process, it produces a standardized document and structured data model that can be inspected before release.

The solution

Extract, normalize, validate, compare, then hand off.

  • Native PDF text extraction with OCR fallback for image-only pages
  • Position-aware field extraction for labeled values, addresses, and ship-to blocks
  • Shared normalization rules with isolated customer-specific exceptions
  • Conservative catalog matching that routes unresolved values to Item Hold instead of guessing
  • Fixed-geometry normalized PDF output for consistent downstream capture
  • Side-by-side source and normalized document review
  • Audited field overrides with source-page evidence and regeneration
  • Exception, retry, rejection, approval, and archive workflows
  • Isolated onboarding for new document layouts before profile activation

Application workflow

A reviewable bridge between dirty documents and clean automation.

The portfolio walkthrough uses fictional records but mirrors the application's operational boundaries: source evidence is retained, normalization decisions are visible, and automation is downstream of validation rather than upstream of it.

Safety by design

The parser is deliberately conservative where certainty matters.

Catalog resolution moves from strongest evidence to weaker evidence: exact canonical identifiers, exact display or vendor identifiers, unique compact matches, tightly bounded decorations, and only then narrowly controlled transformations. Ambiguous or conflicting results do not silently resolve.

The source item number is preserved even when the normalized output uses Item Hold. That separation is important because cleanup should never erase the evidence needed to understand what the sender actually supplied.

Architecture

A reusable normalization layer rather than a one-document script.

A shared default profile contains standard extraction and normalization behavior. Customer-specific profiles layer only the exceptions needed for a particular document layout. JSON Schema validation keeps those rules explicit, while SQLite stores transaction state, audit history, profile requests, and unmatched-item events.

The generated output uses a fixed field map and item-table geometry so downstream capture receives a predictable format regardless of how inconsistent the original PDF was.

Verified clean-room build

Portfolio-safe without reducing the project to a mockup.

The shared package removes production customer profiles, catalog exports, databases, credentials, deployment state, source documents, generated production outputs, and organization-specific identifiers. The included scanner reported zero findings against the supplied clean-room identifier set.

I also ran the included regression suite against this uploaded portfolio package: 186 tests passed. The synthetic smoke workflow processed a fictional purchase order successfully and demonstrated both a valid catalog normalization and a deliberately unresolved item.

Current boundary

PDF intake today; additional structured input adapters can follow.

This portfolio edition currently demonstrates PDF input. CSV and Excel ingestion are natural extensions because the normalization, validation, review, and downstream handoff layers already exist, but those adapters are not presented here as implemented functionality.

The broader operating pattern is document-agnostic: turn variable incoming business data into a clean, validated contract before it is allowed to trigger vendor ordering, ERP entry, accounts-payable processing, or another automated workflow.
